# 01 · 定位与背景：PostgreSQL 在解决什么问题

**学习目标**

读完之后，你应当能够：

1. 用自己的话复述 PostgreSQL 的核心定位（它把什么放在第一位），并说出这份"划算"背后的代价。
2. 判断自己是否属于本课程的目标读者，并知道自己在哪些环节需要补前置知识。
3. 看懂本课程的证据标注约定，知道每一条结论是从哪里来的、可信度有多高。

---

## 1.1 问题的提出

源文档对 PostgreSQL 的定位非常直接：

> 它解决的核心问题是 **"在保证数据绝对可靠的前提下，尽可能让你在一个数据库里做完所有事"**，代价则是你需要接受它更重的运维负担和对使用方式的更高要求。
> — [Source-derived · S-01](07-verification-record.md#s-01)

这句话里有三个可以拆开的东西，恰好构成本课程的三条主线：

| 拆解项 | 含义 | 本课程对应章节 |
| :--- | :--- | :--- |
| 数据绝对可靠 | 事务、约束、MVCC 是地基，不是加分项 | [02 · 核心概念](02-core-concepts.md) |
| 尽量少引入组件 | JSONB 与扩展让一个实例能承担更多职责 | [03 · 核心能力](03-core-functionality.md)、[05 · 相关工具](05-related-tools.md) |
| 更重的运维负担 | VACUUM、膨胀、执行计划需要人主动管 | [04 · 使用](04-usage.md) |

换句话说：源文档没有把 PostgreSQL 定位成"功能更多的关系库"，而是把"少装组件"和"数据不出错"当作主卖点来卖（[S-16](07-verification-record.md#s-16)、[S-21](07-verification-record.md#s-21)），同时诚实地告诉你这笔交易需要用运维精力来付账。

## 1.2 这份"性格"是怎么形成的

源文档把 PostgreSQL 的特性归纳为围绕两个词构建的整体——**正确性**与**可扩展性**：

> PostgreSQL 的特性不是零散的功能清单，而是围绕"**正确性**"和"**可扩展性**"构建的一个整体。
> — [Source-derived · S-02](07-verification-record.md#s-02)

"整体"两个字是理解 PostgreSQL 的关键。它不是"每个维度都拿第一"，而是**维度之间互相咬合**：

- 想让写操作不阻塞读操作 → 必须用多版本并发控制 → 必须产生死元组 → 必须有 `VACUUM` 回收空间 → 运维成本由此而来。（依据 [S-03](07-verification-record.md#s-03)、[R-02](07-verification-record.md#r-02)）
- 想让半结构化数据也能高效查询 → 必须提供 JSONB → 必须让索引认识 JSON 内部结构 → 于是有了 GIN 索引和它的算子类体系。（依据 [S-04](07-verification-record.md#s-04)、[R-05](07-verification-record.md#r-05)）
- 想让一条 SQL 表达复杂分析 → 必须原生支持窗口函数、递归 CTE、LATERAL → **源文档因此称它是"开源关系库中复杂查询表达力的标杆"**——这是源文档的判断，不是已核实的事实。（依据 [S-05](07-verification-record.md#s-05)、[R-09](07-verification-record.md#r-09)、[R-10](07-verification-record.md#r-10)、[R-11](07-verification-record.md#r-11)、[R-12](07-verification-record.md#r-12)）

> 在复杂查询的表达力上，PostgreSQL 是开源关系库中的标杆：**窗口函数、递归 CTE、LATERAL JOIN、FULL OUTER JOIN** 都是原生且完整的。
> — [Source-derived · S-05](07-verification-record.md#s-05)

这三条咬合关系，本课程会在 [02 章](02-core-concepts.md)逐条拆开，并说明每一处"能力"背后拖着什么"代价"。

## 1.3 目标读者

源文档的判断语言指向一类特定读者：已经在做技术选型、需要为"用哪个数据库"负责的人。

> 结合你一贯的选型思维，PostgreSQL 的适用条件可以归纳为一个判断。
> — [Source-derived · S-21](07-verification-record.md#s-21)

具体来说，本课程适合：

- **后端工程师 / 技术负责人**：需要判断某个业务场景该不该上 PostgreSQL，或者该不该从 PostgreSQL 上迁走。
- **正在做"要不要引入 MongoDB / Redis / Elasticsearch"决策的人**：需要知道 PostgreSQL 的能力边界在哪里，否则很容易多引入一个组件。
- **已经用上 PostgreSQL、但运维体感很差的人**：怀疑自己建模或索引策略有问题，需要知道 VACUUM 与执行计划应该怎么看。

不太适合：

- 只想学 PostgreSQL 语法的人。源文档已经明确表态：

> PostgreSQL 的使用门槛不在语法，而在**建模决策和运维意识**。
> — [Source-derived · S-07](07-verification-record.md#s-07)

- 想找一条"最优调优参数清单"的人。本课程不会给这种清单，因为这类清单高度依赖工作负载——这恰恰是 [06 · 学习路径](06-learning-path.md)里要求你自己动手观察的原因。

## 1.5 证据标注约定（请先读这段）

本课程对每一条**事实性结论或源文档主张**都标注来源。标注形式如下：

| 标注 | 含义 | 链接去向 |
| :--- | :--- | :--- |
| `Source-derived · S-xx` | 直接来自源文档 `source.md` 的表述 | [07 章的源定位记录](07-verification-record.md#源定位记录) |
| `Research-derived · R-xx` | 源文档没说或说得不够精确，由本课程查证官方文档后补充 | [07 章的研究记录](07-verification-record.md#研究记录) |
| `Illustrative` | 为了讲清楚而构造的例子，**不主张任何未经查证的行为** | 无链接 |

> **`Source-derived` 不等于"事实"。** 它只表示"源文档这么写"；源文档中的主观判断与经验阈值同样使用这个标签，课程不把它们当作已核实的事实使用（规则见 [07 章的证据标签约定](07-verification-record.md#证据标签约定)）。

四个关键约定：

1. **示例都带标签。** 你会看到 `**示例标签**：Research-derived` / `Illustrative` 这样的行（目前课程中还没有 `Source-derived` 的示例）。构造出来的输出会用"示意输出"这类字样标明，各章措辞略有差异。
2. **源文档没覆盖的事实不会凭空出现。** 本课程为了把话讲透，查证了 PostgreSQL 官方文档、MySQL 官方文档、MongoDB 官方文档以及各扩展官方站点，全部记录在 [07 章](07-verification-record.md#研究记录)，含 URL、检索日期、原文摘录与置信度。
3. **查不到的就标为未解决。** 源文档中有三处断言（一条基准对比、一条厂商案例、一处规模阈值）本课程**没能**找到可信的一手证据，它们没有被删除，而是被降级为"源文档主张 + 未解决问题"记录在 [07 章的未解决问题](07-verification-record.md#未解决问题)。请在引用这三点时保持同等谨慎。
4. **引文做了排版归一。** 为与全课程排版一致，源文档引文中的中文弯引号（“ ”）统一写作直引号（" "），文字内容未改动（约定见 [07 章](07-verification-record.md#证据标签约定)）。

## 1.6 一个贯穿全课程的示例

后面每一章都会用到同一个虚构业务场景，方便你把概念串起来看。

> **示例标签**：Illustrative
>
> 某电商系统需要存三类数据：订单（强结构、高频按状态过滤）、商品属性（每个品类不同、字段会变）、用户行为事件（半结构化、只写不改、需要按任意维度检索）。
>
> 问题：如果只允许你选一个数据库，你会选什么？如果允许你选两个呢？

这个场景没有标准答案，它的作用是逼你在每一章结束时回到它：

- [02 章](02-core-concepts.md)会告诉你，"订单表高频 `UPDATE` 状态"这一步在 MVCC 下意味着什么。
- [03 章](03-core-functionality.md)会告诉你，商品属性放 JSONB 后，索引该怎么建。
- [04 章](04-usage.md)会告诉你，如何用 `EXPLAIN ANALYZE` 验证你建索引前后的差别。
- [05 章](05-related-tools.md)会告诉你，行为事件这一路可能根本不该放在 PostgreSQL 里。
